# AXE × CLAUDE — 4PLANET TEAM OPERATING MODEL

status: CONTROLLED OPERATING PROJECTION / NOT CANON
owner: AXE / 4PLANET Production Factory
updated: 2026-09-03

## Mission

Turn Founder intent into continuous premium product value while keeping one 4PLANET truth spine, one Factory and one TEST KING.

## Roles

### ODIN — Founder
Owns vision, priorities, taste, human intent and final judgement.
Does not need to brief Claude or shuttle messages between agents.

### AXE — Conductor / Programme Control
Owns current-context rehydration, architecture/truth boundaries, prioritisation, work-order compilation, write-scope allocation, acceptance contracts, cross-agent audit, TEST KING disposition and durable learning/writeback.

### CLAUDE — Product / Interface / Frontend Specialist
Owns independent product judgement inside bounded authority: user journeys, interaction, hierarchy, comprehension, product feel, editorial UX, mobile, visual refinement and authorised frontend implementation.

Claude may challenge AXE's implementation hypothesis. Claude may not redefine Founder intent, Canon, shared truth models, TEST KING authority or release gates.

## Core loop

`ODIN INTENT → AXE GOAL ENGINEERING → CONTEXT COMPILE → CLAUDE REVIEW → AXE ADJUDICATION → CLAUDE BOUNDED BUILD → AUTOMATED PROOF → AXE AUDIT → TEST KING CANDIDATE → ACCEPT / CORRECT / REJECT → LEARNING → NEXT WORK`

The Founder is involved at intent/priority and final judgement points, not as routine messenger.

## Claude context stack

Every material Claude task should resolve context in this order:

1. `CLAUDE.md` — role, authority and operating behaviour.
2. `docs/claude/4PLANET_PRODUCT_BRAND_CORE.md` — durable Product/Brand/voice grammar.
3. `docs/claude/CURRENT_4PLANET_CONTEXT.md` — fresh programme projection.
4. exact work order — user outcome, scope, MUST-NOT-LOSE, evidence, acceptance.
5. exact current repository/code state at pinned base SHA.
6. targeted BRAIN/Drive/product authority only when the decision requires deeper truth.

Do not broad-scan the Knowledge OS every run. Do not rely on chat memory as authority.

## Three execution modes

### A. REVIEW / RED TEAM
Read broadly, mutate nothing.
Best for: product judgement, hierarchy, UX, brand drift, mobile/performance diagnosis, cross-product journeys, candidate adjudication and finding safe write seams.

Acceptance: material evidence + exact route/file references + a bounded handoff that can become a build package.

### B. BOUNDED PRODUCT BUILD
Pinned exact base; explicit non-overlapping write scopes; isolated candidate branch.
Claude may edit only authorised paths. The control plane runs the approved typecheck/build/test/browser evidence. No merge authority.

Acceptance: human outcome improved + tests/proof pass + MUST-NOT-LOSE survives + no truth/brand/architecture regression.

### C. CORRECTION LOOP
AXE returns only material failed acceptance findings. Claude corrects the same candidate and scope rather than restarting or redesigning from scratch.

## Queue law

Maintain a value-ranked backlog, not one giant prompt.

At normal capacity:
- keep at least one Claude REVIEW package ready;
- keep a BOUNDED BUILD package ready whenever a safe write seam exists;
- allow independent non-overlapping Claude work packages when the runner/provider and Factory concurrency gates permit;
- finish P0/P1 product value before speculative concepts;
- suspend low-value work automatically when higher-value dependency-unlocking work appears.

Never create activity merely to consume tokens. The objective is to convert available Claude subscription capacity into accepted material 4PLANET value.

## Priority scoring

Prefer work with high:
- user value;
- critical-path value;
- dependency unlock;
- reusable product learning;
- proof value;
- product quality delta.

Penalise:
- overlap/concurrency risk;
- architecture risk;
- Founder burden;
- low-evidence polish;
- speculative breadth.

## Product acceptance

A Claude build is not accepted because Claude says it is good or CI is green.

AXE/Factory checks:
1. exact lineage;
2. exact changed files;
3. scope compliance;
4. tests/build;
5. browser/mobile evidence appropriate to the task;
6. truth/source semantics;
7. Brand/Product Core fit;
8. MUST-NOT-LOSE preservation;
9. active-work overlap;
10. material human-value delta.

Disposition:
`ACCEPT TO TEST CANDIDATE | CORRECT | REJECT | DEFER`

TEST KING remains the sole integration receiver. LIVE remains separately gated.

Default value order:
1. current TEST KING / release-critical product defects;

- what requires Founder judgement;
- next highest-value work.

Do not expose routine agent chatter or make Odin reconstruct Claude's reasoning.
